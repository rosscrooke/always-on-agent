Always-On Ops Agent: Exercise Details & Implementation Approach

Partner Basecamp hackathon · data: day2/03_hackathon/always-on-agent (fork of rosscrooke/always-on-agent) · written 2026-10-23

Summary

The exercise: build an always-on agent (a Claude "routine" that runs on a schedule or trigger) and point it at a synthetic enterprise repo. On each run it should:
  1. Triage open production incidents. Set severity, find the root cause, link the matching runbook, and propose the fix.
  2. Correlate incidents with recent deploys.
  3. Scan vendor contracts for compliance drift against a written policy, and open an issue for each violation.
All the data is fictional.
What's from the repo and what's inferred.
  • From the repo: the data files, the jobs described in its README, and the compliance policy's wording. The README names "Card C — Compliance Drift" and tells you to "point your routine at this repo via the Routines UI".
  • Not in the repo: the hackathon brief itself (partner-basecamp-hackathon/01-always-on-ops-agent), including the full set of cards and the Routines setup.
  • Inferred: the triage and deploy-correlation jobs (presumably the other cards), and everything under "Expected answers". Those answers are my reading of the data. Check them against the official brief.

Links and traps a strong agent should catch

  • One bug, two incidents. PROD-4521 (all guest-checkout traffic after the payment deploy) and PROD-4487 (Acme after the cohort-B flag) share the line-142 root cause. The agent should link them, and the fix for one informs the other.
  • Red-herring deploys. The frontend pricing-copy deploy shortly before PROD-4487, and the auth-service Redis deploy near PROD-4498, are both close in time and both wrong.
  • Ambiguous timing. On PROD-4519 the symptom starts before the deploy. A good agent states that uncertainty and follows the runbook's first check instead of blaming the deploy outright.
  • "Don't" lists. The auth runbook says don't scale pods and don't raise the load-balancer timeout. A recommendation that does either should count as a failure.
  • Not everything is an incident. PROD-4506 shouldn't get a severity or a page.
  • Severity needs a reason. Only the payment runbook defines severities. For the others, the agent should state its reasoning rather than invent policy.

Judgement calls the agent must handle honestly

  • Acme's audit clause (60 days): it falls between "must be ≥ 30 days" and "violation if > 90". The agent should flag it as a gap for review, not a hard violation, and say why.
  • "Cap excludes data breach": Acme and Globex carve breach out of the cap, so they're uncapped for breach, which favours us. Sirius applies its cap to breach claims, at only 3 months. The agent should read what each clause actually does, not just match the word "breach".
  • Governing law isn't a closed list ("…or similar"). California and Malaysia need a stated rationale and should go to a human, not be answered with false certainty.
  • Globex is the control case. An agent that flags violations on Globex is producing false positives, which is just as important to measure as missed violations.

Agent design

One run of the agent:

  1. LOAD STATE       which issues/contracts were already processed (content hash per file)
  2. TRIAGE           for each new/changed issue:
                        classify (incident vs. request) → match runbook → correlate deploys (time window + service + files)
                        → severity (runbook guide, else stated reasoning) → recommended action (respect "Don't" lists)
  3. LINK             group incidents sharing a root cause (e.g. PROD-4521 ↔ PROD-4487)
  4. COMPLIANCE       for each new/changed contract × 7 policy rules → compliant / violation / needs-review, with quote
  5. WRITE BACK       one comment/label update per issue; one new issue per violation (idempotent)
  6. REPORT           run summary: what changed, what was paged/recommended, what needs a human

Prompt structure: a stable system prompt (the role, the output rules, and the full compliance-policy.md and runbooks as a frozen prefix for caching), then the changing content (one issue or one contract) in the user turn.

Tools and output schemas

Tool (Option B)Purpose
list_files(dir) / read_file(path)Read issues, runbooks, deploys, contracts and the policy
find_deploys(service?, since, until)Search the deploy log in a time window, so the model doesn't scan raw JSON
update_issue(id, severity, labels, comment)Write the triage back: a PR that edits the JSON, or a GitHub issue comment
open_issue(title, body, labels)One compliance-violation issue per contract × rule
escalate(who, reason)Recommend a page. It records the recommendation, but a human sends it.

Guardrails

  • Recommend, don't act. The runbooks contain operational commands (ssh, config changes, redeploys, rollbacks). The agent proposes them in comments and never runs them. Rollbacks and pages need human approval.
  • Idempotent writes. Track processed items by content hash, so a re-run doesn't repost comments or open duplicate compliance issues.
  • Cite everything. Every claim points to a file and line, section or field (deploy time, stack trace, contract §). If there's no citation, it's marked "needs human".
  • Honest uncertainty. Ambiguous cases (PROD-4519's timing, Acme's 60-day audit clause, governing law) are flagged needs_review with reasons.
  • The fork is public. Anything the routine commits or comments on vijayignatius/always-on-agent is public. The data is synthetic, but don't add real names, tokens or internal URLs.

Run it 3–5 times and report pass rates, since the Day 2 lesson was to read the rate, not a single run. Pace the runs to stay under the gateway rate limit.

Cost and latency levers (from the inference lab)

  • Route by job. Haiku for "incident or request?" and the per-rule compliance checks; Sonnet for root cause and deploy correlation.
  • Cache the frozen prefix. The policy and runbooks are identical on every call. Measure the cache hit rate, which is intermittent on the gateway.
  • One schema call per item instead of free-form reasoning followed by JSON, with max_tokens sized to the record and effort: "low" on Sonnet.
  • Only process what changed. The biggest lever for an always-on agent is not re-analysing unchanged files on every run.

With three developers, steps 3–6 run in parallel. See Team split.

Agent prompt (prompts/triage.md), which the routine runs:

You are the on-call triage agent for the BTS platform (all data is synthetic). On each run, triage every
open issue in issues/ that has no record in out/triage/ or whose content has changed.

For each issue:
1. Decide is_incident. Feature requests and enhancements are NOT incidents: no severity, no page,
   label "enhancement", route to the backlog.
2. Match a runbook in runbooks/ by symptoms. Quote the runbook section you relied on.
3. Correlate with deploys/recent.json: a deploy is a suspect only if it happened BEFORE the symptom
   started, within a plausible window, AND its service or changed files relate to the symptom. Explicitly
   rule out nearby deploys that don't fit (say why). Feature-flag deploys count — check which tenants they
   affect. If timing is ambiguous, say so and follow the runbook's "first check" instead of blaming a deploy.
4. Severity: use the runbook's severity guide when one exists (e.g. all customers → P0, one tenant → P1).
   Otherwise choose and state your reasoning; never invent policy.
5. Link issues that share a root cause (linked_issues) and say what the shared cause is.
6. recommended_action: concrete next steps from the runbook. Prefer rollback when rollback_available is
   true. Respect every "Don't" in the runbook. Never execute anything — recommend only; paging and
   rollbacks need a human.
7. Every claim in root_cause must be backed by an entry in evidence that cites a file and field/line
   (e.g. "deploys/recent.json: payment-service v4.8.2 deployed_at 14:04:11Z"). If you can't cite it,

Agent prompt (prompts/compliance.md), which the routine runs:

You are the vendor-contract compliance agent. Check each contract in contracts/ against EVERY rule in
compliance-policy.md and return one finding per contract × rule (7 per contract).

For each rule:
1. Find the clause that governs it. Quote it exactly with its section number. If the contract is silent,
   say so — silence is a violation only where the policy says so (e.g. data residency).
2. Apply the policy's own "Violation:" definition literally, then its requirement:
   - status "violation"   → the clause meets a listed violation condition.
   - status "compliant"   → the clause meets the requirement.
   - status "needs_review" → it is neither (e.g. it misses the requirement but isn't a listed violation,
     or the policy says "or similar" and the jurisdiction isn't named). Explain why a human must decide.
3. Read what a clause actually does, not keywords. A liability cap that does NOT apply to data breach
   (breach is uncapped) favours us; a cap that DOES limit breach claims below 12 months' fees is a violation.
4. Note relevant terms the policy doesn't cover (e.g. long auto-renewal notice) in reason, but don't
   mark them as violations.
5. Be precise about numbers: compare notice periods, windows and caps exactly against the thresholds.

Output exactly one JSON object per finding matching schemas/compliance_finding.json, nothing else.

Orchestrator prompt (the routine's top-level instructions):

You are the Always-On Ops Agent for this repository. Each run:

1. Read state.json. Work only on files in issues/ and contracts/ that are new or changed since the last
   run. If nothing changed, write a one-line "no changes" entry to out/run-report.md and stop.
2. For each new/changed issue, follow prompts/triage.md and write out/triage/<id>.json.
3. For each new/changed contract, follow prompts/compliance.md and write out/compliance/*.json.
